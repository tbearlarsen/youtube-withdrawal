The real, current deployment (confirmed via `home-server`'s own docs and the user directly) has it as its **own** separate compose stack (`/docker/youtube-withdrawal/compose.yaml`), just joining TubeArchivist's Docker network to reach it by hostname. Lesson for future-me: a recovered memory fragment describes a plan or an early state, not necessarily what shipped — verify against the real deployment (or ask) before treating it as current.

2. **Where Claude Code runs for this project changed.** The user isn't fully certain Claude Code was ever used from a separate Mac for this project (the recovered `user-profile.md` memory implies local dev on a Mac, but this wasn't confirmed). Going forward as of 2026-09-01: Claude Code runs directly on VM101 via code-server, in the same working directory the Docker deploy builds from — no separate dev-machine-to-server step. `directives/deploy.md` assumes this; if that setup ever changes back to a separate dev machine, that directive needs updating, not just this note.

3. **`directives/deploy.md` was written with no `execution/` script behind it — caught by the user directly, same session.** The user asked, correctly: if a directive is one part of a workflow, shouldn't there be an execution half? There should have been. The directive originally had Claude type `git pull` / `docker compose up -d --build` / `docker ps` / `curl` by hand every time, exactly the "push mechanical steps into a script" principle this whole architecture exists for, just not applied. Fixed same session: `execution/deploy.sh` now does the full sequence with a hard pass/fail exit code, `directives/deploy.md` just calls it. Lesson: a directive whose steps are already fully mechanical (no LLM judgment in any step) is a strong signal a script belongs in `execution/`, even for a project this small — "the project is small" isn't a reason to skip Layer 3, it's a reason there's only one directive that needs it so far.

4. **The code-server working directory is *not* `/docker/youtube-withdrawal` — confirmed 2026-09-02, and it matters more than the earlier "unconfirmed" note below suggested.** This session runs from `/data/projects/youtube-withdrawal`, a separate git checkout on the same host. Confirmed by diffing it against `/docker/youtube-withdrawal`: different `.git` state, and `data/*.json` had already diverged between the two (harmless — that dir is gitignored runtime state, and `/docker/youtube-withdrawal/data/` is the one that's actually live). The part that *does* matter: **this checkout's shell has no `docker` binary and no `docker.sock` at all** — not a PATH issue, confirmed absent everywhere reasonable. `execution/deploy.sh` and `directives/deploy.md` were written assuming Claude Code could run `docker compose` directly from here; it cannot, from this checkout or any other, because the container itself has no docker access. **Standing rule going forward, per the user directly:** the user always runs docker commands themselves, from wherever they actually have docker access — Claude edits compose/config files (it does have plain file read/write on `/docker/*`, just not the docker CLI) and hands over exact copy-pasteable commands. `directives/deploy.md` needs updating to reflect this — it currently reads as if Claude runs `execution/deploy.sh` itself.
5. **`data/*.json` in this checkout vs. `/docker/youtube-withdrawal/data/`:** don't treat this checkout's local `data/` as representative of live app state — it's a stale clone-time snapshot (gitignored, never synced back). For anything needing real current state (what's actually requested/favorited/auto-downloading right now), read `/docker/youtube-withdrawal/data/*.json` directly, or query TA's API for ground truth.
6. **A locally-tracked video ID (e.g. in `requested.json`) can go stale if TA state is changed *outside* the app's own flow (its API called directly, not through the app's buttons).** Hit this directly 2026-09-02: deleted a video from TA via direct API call to fix a corrupt download, and the app's `requested.json` still listed it — TA's own hourly channel rescan re-added the video as `pending` fine, but the app's pending/channel views don't filter on `requested_ids` (checked `app/routers/pending.py` and `app/routers/videos.py` directly — they only filter on the `deleted` tracker), so this wasn't actually the cause of the video briefly not appearing; that was just a timing issue (checked before TA's rescan re-added it). Recorded here anyway because it's a real edge case worth knowing about: any tool that changes TA state directly (bypassing this app's own request/ignore/restore endpoints) can leave `requested.json`/`deleted.json`/`auto_download.json` pointing at stale reality. The app's reconciliation (see `CLAUDE.md`'s Canonical Data section) only runs "on startup and on queue page loads," and only for `requested.json` specifically — it doesn't cover every path.
7. **Two sharp, non-obvious bugs found building `/docker/ta-sponsorblock-chapters/` — relevant to any future tool that reads/writes TA's downloaded media files directly, not just this one:**
   - **`ffmpeg -f ffmetadata -` (dumping a file's metadata as text) is unsafe on real TA downloads.** TA embeds the video's thumbnail as a second, attached-picture MJPEG stream. Dumping metadata as text can leak that image's raw JPEG bytes into stdout/stderr, which crashes anything doing `subprocess.run(..., text=True)` with a `UnicodeDecodeError` — confirmed by reproducing it directly against real library files (`KCpUk0yCjFE`, `uoFWpZ4CDs4`, and 15 others all hit this identically). Fix: use `ffprobe -show_format -show_chapters -print_format json` instead (its own JSON serializer safely replaces invalid bytes) and never use `text=True` on a subprocess touching one of these files — capture bytes, decode with `errors="replace"` only where actually needed.
   - **TA embeds a large custom `ta` metadata tag (the video's full JSON — description, channel info, even signed subtitle URLs) plus a few tags (`channel_icon`, `channel_banner`, `channel_tv`) that contain genuinely non-UTF-8 binary data.** A naive "read all metadata as text, modify, write it all back" approach will silently corrupt those tags on every single video, not just edge cases. Fix: never read-modify-write the full tag set — leave original metadata completely untouched via `ffmpeg -map_metadata 0` and add only new chapters from a separate, minimal file via `-map_chapters 1` (plus `-movflags use_metadata_tags` on the write, or MP4's muxer silently drops non-standard tags even when copying). Verified this preserves every original tag byte-for-byte against a real file.
   - Also confirmed empirically (not assumed): MP4/MKV chapters are timeline **breakpoints**, not independent ranges — the muxer silently snaps each chapter's end to the next chapter's start and forces the first chapter to start at 0. Inserting an isolated `[start,end]` chapter without accounting for this corrupts the surrounding chapter boundaries. `embed_sponsorblock.py`'s `build_partition()` builds a full non-overlapping partition of the whole timeline for exactly this reason — don't "simplify" that back to naive isolated-chapter insertion.
8. **Known, accepted limitation: Jellyfin's Intro Skipper plugin cannot be told to re-analyze a single item.** Checked every controller it exposes (`SegmentEditorController`, `TroubleshootingController`, the Tools tab) — the only reset mechanism is "Rebuild Local Database," which wipes the *entire* library's analysis state. Its skip-reanalysis hash is computed only from `(plugin config, mode, action, ffmpeg capability)` — never from the file itself — so a video analyzed once before `ta-sponsorblock-chapters` later embeds chapters into it (because SponsorBlock data arrived late from the community) will never be picked up again without a full-library rebuild+reanalyze. User's call 2026-09-02: leave this alone for now, don't automate a periodic rebuild. Revisit only if asked.
